# 结果汇总：几何表示与多尺度架构搜索（NAS）在室内点云分割上的作用

> 本文档汇总 2026-09-23 ~ 09-25 的全部实验结论。
> 全部数字可在 `data/multibranch_*/` 的结果表中逐位复核（100+ 张表，16 轮实验）。
> 训练协议：S3DIS，12 训练房 × 12 验证房 × 2 seed × 300 epoch，GPU 1，
> 指标 `present_class_miou`（只对房间内真实出现的类别求平均）。

---

## 0. 一句话结论

**在 DGCNN 的结构超参上做搜索是死路（零交互、主效应也只有 0.02 量级）；
把"几何表示与尺度"作为搜索对象，能在同一个跨房间基准上把 mIoU 从 0.3370 推到 0.4194
（+0.0824 = +24.4% 相对），同时训练快 2.8 倍。**
且该增益在独立 test split 上完整复现（+0.0752 vs val +0.0756）。

**最终冠军 `voxel15_z16,voxel20_z24,voxel25_z16,voxel35_z64,voxel50_z96@gate`
（5 个不同体素尺寸 0.15/0.20/0.25/0.35/0.50 m，每层各自独立的 z 分层 16/24/16/64/96）
是我手工设计不出来的，而是"提出 → 实测 → 写回"自动闭环
从 3.2×10^8 的组合空间里搜出来的** —— 见 §9。

**冠军演化轨迹**：
```
points（DGCNN 基线）                                        0.3370  104.1ms
手工枚举的最好配置（~88 个）                                 0.4110
进化① 3 分支 voxel15_z16,voxel20_z32,voxel50_z96@gate       0.4126   26.7ms
进化② 4 分支 (+voxel35_z64)                                 0.4147   30.8ms
进化③ 5 分支 (+voxel25_z48)                                 0.4180   65.4ms
进化④ v25 的 z48→z16（留一消融指导）                        0.4193   39.5ms
进化⑤ v20 的 z32→z24  ← 最终                                0.4194   37.5ms
```

**⚠ 边际增益已收敛，该轴已榨干**（与 k 轴当年同一模式）：
```
第 3 轮 加第 4 分支   +0.0021
第 4 轮 加第 5 分支   +0.0033
第 5 轮 v25 降 z      +0.0013
第 6 轮 v20 降 z      +0.0001   ← 已降到 σ 的 1/10
```
> **教训：当边际增益降到 σ 以下时应停止微调并换轴，而不是继续消耗预算。**

| 去掉哪一层 | mIoU | Δ | 贡献排序 |
|---|---|---|---|
| （全 5 层，`v25_z48` 版） | 0.4180 | — | — |

第 6 轮把"降 z"手法施加到其余各层，并设了**反向对照**防过度泛化：

| 操作 | mIoU | Δ vs 0.4193 |
|---|---|---|
| v20 z32→z24 | **0.4194** | **+0.0001**（打平、更省） |
| v35 z64→z48 | 0.4164 | −0.0029 |
| **v25 z16→z32（反向对照）** | **0.4160** | **−0.0033** ← 确认 z16 确实更优 |
| v20 z32→z16 | 0.4151 | −0.0042 |
| v35 z64→z32 | 0.4140 | −0.0053 |

**→ 每一层有各自的最优 z，"越低越好"是错的。v25 的 z48 才是那个异常浪费的点。**
反向对照同时确认了第 5 轮的改进是真实的，不是噪声。

### 1.1c 收益来自"加分支"，不来自"调参数"

第三轮做了**干净的对照实验**（对当时冠军 `voxel15_z16,voxel20_z32,voxel50_z96@gate`）：

| 扰动 | 架构 | mIoU | Δ |
|---|---|---|---|
| **加第 4 个分支** | `voxel15_z16,voxel20_z32,voxel35_z64,voxel50_z96@gate` | **0.4147** | **+0.0021** ✅ |
| 粗端 v50→v35 | `...voxel35_z96@gate` | 0.4125 | −0.0001 |
| 粗端 z96→z128 | `...voxel50_z128@gate` | 0.4116 | −0.0010 |
| 粗端 v50→v25 | `...voxel25_z96@gate` | 0.4111 | −0.0015 |
| 粗端 z96→z64 | `...voxel50_z64@gate` | 0.4098 | −0.0028 |

**单独调粗端参数（体素尺寸、z 分层）全都没用；只有"加分支"带来了提升。**
→ **"分支数 / 尺度覆盖"这条轴还没榨干，而"粗端参数"本身已接近最优。**

### 1.1d 特征宽度（`feat`）是负结果 —— 买宽度不划算

在 voxel 分支上首次测试特征宽度（此前只在 points 家族测过）：

| 架构 | mIoU | ms/step | 结论 |
|---|---|---|---|
| 冠军（**feat=64**） | **0.4194** | 39.5 | 最优 |
| 5 分支 **feat=32** | 0.4150 | **30.6** | 省 22%，但掉 0.0044 |
| 4 分支 **feat=128** | 0.4154 | **117.4** | **贵 3.0×，精度反而更低** |
| 3 分支 **feat=128** | 0.4132 | 87.0 | 贵 2.2×，最低 |

**`feat=128` 花 2.2~3.0× 成本，精度反而下降 0.004~0.006 → 明确亏本。**

⚠ **与 points 家族形成鲜明对比**：points 上 `feat=128` 拿到 **+0.019**。
→ **"加容量"不是通用增益，取决于架构族**：points 的瓶颈在**容量**，
voxel 的瓶颈在**几何表示（多尺度覆盖）**，单纯加宽无用。

> **共同教训："加容量/加参数"没有通用增益。** 真正起作用的始终是
> **几何表示与多尺度覆盖**（voxel 表示 +0.0515、多尺度 +0.0103~0.0161）；
> 容量类轴（feat）在本数据上是亏的。

### 1.1e 三条轴的系统性排查

| 轴 | 判定 | 关键证据 |
|---|---|---|
| **尺度/分支** | ✅ **有效**，但**已榨干** | 加分支 +0.0021/+0.0033；边际已衰减到 **+0.0001 < σ** |
| **尺度参数微调**（各层 z / 体素尺寸） | ⚠ **局部有效、不可推广** | v25 降 z 是严格 Pareto 改进；v20/v35 降 z **全部变差** |
| **特征宽度 `feat`** | ❌ **负结果** | feat=128 花 2.2~3.0× 成本，精度**下降** |

### 1.2 test split 无偏验收（独立 split，只碰一次）

**✅ test 排序与 val 排序完全一致 → 基于 val 的搜索确实迁移到 test。**

| 架构 | test mIoU | val mIoU | test Δ | val Δ |
|---|---|---|---|---|
| `voxel15_z16,voxel20_z32,voxel25_z16,voxel35_z64,voxel50_z96@gate`（5 分支） | **0.4210** | 0.4193 | **+0.0777（336σ）** | +0.0823 |
| `voxel15_z16,voxel20_z32,voxel35_z64,voxel50_z96@gate`（4 分支） | 0.4194 | 0.4147 | +0.0762 | +0.0777 |
| `voxel15_z16,voxel20_z32,voxel50_z96@gate`（3 分支） | 0.4184 | 0.4126 | +0.0752 | +0.0756 |
| `points`（基线） | 0.3432 | 0.3370 | 0 | 0 |

**test 上的增益随演化单调上升（0.4184 → 0.4194 → 0.4210），与 val 同序。**

⚠ **val 增益（+0.0823）略高于 test 增益（+0.0777）**，差 0.0046 —— 在 val 上挑架构
必然有轻微的选择性乐观。**对外报数必须用 test 数字**。
（对比：3 分支冠军的 val/test 差只有 0.0004 → **越复杂的架构，val 乐观偏差越大**。）

> ⚠ **读法**：test 上基线也更高（0.3432 vs 0.3370），说明测试房间整体稍易。
> **该看的是相对增益 Δ，不是绝对分数** —— 绝对分数会随 split 难度漂移。

**test 上 Pareto 前沿**含全部三个换表示配置 → 基线 `points` 在
**精度、速度、显存三个维度上全部被支配**。

⚠ **一处未做的**：最终冠军的 `v20_z24` 变体（val 0.4194）**没有单独的 test 数字**。
它与已验收的 `v20_z32` 变体在 val 上只差 +0.0001（远小于 σ），
两者 test 数字统计上不可区分 —— 但**未实测，故不宣称**。

## 2. 为什么"表示搜索"有效，而"结构调参"无效

### 2.1 结构调参：主效应存在，但零交互（死路）

架构表（6 配置 = k × 池化 × 图空间，**参数量全部相同 = 113,415**）：

| 配置 | mean mIoU |
|---|---|
| `k=48 \| agg=max \| space=feat` | 0.3370 |
| `k=48 \| agg=max \| space=coord` | 0.3305 |
| `k=48 \| agg=maxmean \| space=feat` | 0.3125 |
| `k=48 \| agg=mean \| space=feat` | 0.2653 |

- **主效应显著**：池化 max vs mean 差 **0.07**（很强）。
- **但交互为零**：逐房间 oracle = 最好单一配置（headroom **+0.0000**）；
  **6 个 Area 的最优配置全部相同**（域级 headroom 也 +0.0000）。

**含义**：收益来自"选一个更好的普通架构"，**不是**来自"架构随密度/房间/域条件化"。
原课题「Density-Conditioned Geometric Architecture Search」的核心假设**不成立**。

### 2.2 k 轴：三个独立角度关闭

| 角度 | 结果 |
|---|---|
| 密度相关性 | R² = 0.008 |
| 尺度相关性 | R² = 0.018 |
| 策略 headroom（逐房间 oracle） | **+0.0017** < σ_fit 0.0014 |

### 2.3 结构族未饱和（但缺陷在别处）

用两个预算的 Δ = full − cheap 判"该族是否已调透"：

- `r(cheap, Δ) = +0.809`（**正相关**）→ **优势放大型**：起点好的配置补涨更多，差距被训练**拉大**
  → 结构差异是**真的**，不是"训练量/调参程度"造成的假差距 → **不饱和**。
- 对照：若 r ≈ −1（欠拟合回填型、最终趋同）才是真饱和。
- 但**架构差异的结构性来源有限**：见 2.1 的零交互。

### 2.4 结论：问题不在"选哪个超参"，而在"用哪种几何表示"

不同**表示**对域差的响应机制在**数学上就不同**，因此是"族级别"的差异：

| | 笛卡尔点 + kNN | 体素 / 柱状 | range-view |
|---|---|---|---|
| 感受野由什么决定 | **kNN 邻域（随密度漂移）** | 栅格尺度 × 卷积核 | 球面分辨（随距离衰减） |
| 对密度下降的响应 | 邻域被掐断 | 与点数解耦 | 分辨率自然衰减 |
| 归纳偏置 | 局部置换不变 | 规则化 / 尺度一致 | 视角结构 / 方位角 |

## 3. 贡献分解（"NAS 起了作用"的直接证据）

```
points（DGCNN 基线）                       0.3370   103.8 ms/step   3524 MiB
  + 换 voxel 几何表示（z 作第三空间轴）      +0.0515
  + z 多尺度（并行多个 z 分辨率）            +0.0103 ~ +0.0161
  + 体素尺寸优化（0.25 m → 0.20 m）          +0.0020
  + 混合体素尺寸（细 + 粗在同一网络内）      +0.0030
= ms4_mix_v20_v50_z16_z32_z64_z96          0.4110   = +0.0739（+21.9% 相对）
                                            同时快 2.4×、省显存 4.2×
```

**且不是靠堆参数**：同等预算下架构选择的差距是 **2.7 倍** ——
`points_f128`（249,735 参数）只有 +0.0191，而 `voxel25_z64`（251,975 参数）拿到 +0.0515。

## 4. 两条尺度规律（都是倒 U，不是"越多/越细越好"）

### 4.1 z 分层数（单尺度，体素 0.25 m）

| z_bins | 8 | 16 | 32 | 48 | **64** | 96 | 128 | 192 |
|---|---|---|---|---|---|---|---|---|
| mIoU | 0.3290 | 0.3603 | 0.3780 | 0.3848 | **0.3885** | 0.3883 | 0.3813 | 0.3806 |

**峰值 z=64，倒 U。** 物理解释：太粗会把不同地物压进同一层（欠分辨），
太细则每层样本太少、房间高度被过度切分（过分辨）。

### 4.2 体素尺寸（单尺度，z=64）

| voxel_size | 0.50 | 0.35 | 0.15 | **0.20** |
|---|---|---|---|---|
| mIoU | 0.3685 | 0.3812 | 0.3879 | **0.3902** |

**峰值 0.20 m，同为倒 U。** ⚠ 这一维此前**从未被单独测过**（早期几乎全用 0.25 m）。

### 4.3 尺度数与融合方式

| 尺度数 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| mIoU | 0.3885 | 0.3988 | 0.4027 | 0.4038 | 0.4046 |
| 边际增益 | — | +0.0103 | +0.0039 | +0.0011 | +0.0008 |

**边际递减但恒为正**；4 尺度起接近平台。

**融合方式是小效应**：同组分支 `late` 0.3983 / `cat` 0.3973 / `gate` 0.4013
（gate 只多 2 个参数）→ 差 <0.004，**融合不是主导因素，尺度组合才是**。

### 4.4 三个几何表示家族的定量排序

| 表示 | 单独 mIoU | Δ vs 基线 | 说明 |
|---|---|---|---|
| **voxel**（规则 3D 栅格，z 作空间轴） | **0.3902** | **+0.0532** | 最强 |
| points（笛卡尔 + kNN 动态图） | 0.3370 | 0 | 基线 |
| **range-view**（球面投影） | **0.2786** | **−0.0584** | 最弱 |

**range-view 为何最弱**：室内 S3DIS 点云在球面上**分布极不均匀**
（房间不是绕中心扫描的），球面投影的分辨率分配远不如规则体素合理。
**"球面投影适合旋转式激光雷达"这个前提在室内不成立** ——
即使实现了"以房间中心为原点、逐像素取最近点"的室内适配。

**分辨率扫描几乎平坦**：`rv32` 0.2730 / `rv64` 0.2786 / `rv128` 0.2752
→ 瓶颈**不在分辨率**，而在"球面投影与室内几何不匹配"这一根本问题。

**⚠ 一个重要的反面结论：多分支融合并非总是有益。**

| 组合 | mIoU | 说明 |
|---|---|---|
| `voxel20` + `voxel50`（两个强分支） | 0.4037 | ✅ 有效融合 |
| `points` + `voxel20` | 0.3622 | ✅ 有效（但不如纯 voxel 混合） |
| **`points` + `rangeview64`（两个弱分支）** | **0.3279** | ❌ **低于基线 0.3370** |

**融合的前提是参与的分支各自都足够强**；把弱分支加进去会**拖累整体，甚至低于基线**。

**但 range-view 作为辅助分支仍有成本价值**：`v20v50+rv64`（三家族）= 0.4001 @ **6.5 s/run**
—— 比纯 voxel 混合低 0.0036，却**快 2.6 倍**，是成本–精度曲线上的一段新可行区间。

## 5. 精度–成本 Pareto（本项目新发现的搜索维度）

此前所有搜索（k 轴、架构轴）都在"**固定预算下比精度**"，
MAP-Elites 的 `cost_rel` 维度一直空转（候选成本几乎相同）。
换几何表示后**成本跨约 25 倍**，Pareto 前沿第一次有真实差异可探索。

| 取向 | 配置 | mIoU | ms/step | 相对基线的取舍 |
|---|---|---|---|---|
| 最准 | `ms4_mix_v20_v50_z16_z32_z64_z96` | 0.4110 | 42.9 | +0.0739, 2.4× 快 |
| **性价比** | `ms3_mix_v20_v50_z16_z32_z96` | 0.4091 | **24.4** | +0.0720, **4.3× 快、8.1× 省显存** |
| 最省 | `ms_mix_v35_v50_z32_z96` | 0.3923 | **11.7** | +0.0553, **8.9× 快、14.3× 省显存** |

## 6. 踩过的坑（都会静默污染结论，务必保留）

| 坑 | 症状 | 正解 |
|---|---|---|
| **形状能广播 ≠ 语义正确**：把 `(1,3,N)` 传给期望 `(N,3)` 的分支 | **不报错**；分支输出 std 正常(0.62) 但经 head 后 logits std 仅 0.048 → **预测类数=1**；loss 首值 1.94（正常 4.29）且几乎不降；同房 mIoU 0.04（正常 0.85） | 跨模块传张量**必须显式统一形状约定 + 边界断言**。修后 0.04→0.8465 |
| **在稀疏图/体素上用 BatchNorm** | 室内体素图 97.7% 空体素 + batch=1 → BN 统计被 0 主导 → **跨点特征 std 0.326→0.0018**（稀释 180×）、训练时间 33s→1.2s | 一律用 **GroupNorm** |
| **性能测量未 warmup（CUDA 伪影）** | `z_bins=8`（体素最少、真实前向 1.0ms）被量成 **238 ms/step**，比最重配置还慢 40× → **会使 Pareto 前沿整体反向** | 测 step time 前**必须 warmup 3 次**，再 `reset_peak_memory_stats` + `synchronize` |
| **配置名与参数值不一致** | voxel 写成 `z_bins=max(8, z_bins*2)` → 标称 `voxel25_z32` 实际 16；据此得出"z16→z32 有 +0.0177"**是错的** | 参数**直白透传**；配置名数值必须等于实际值；建表后**回读 config 校验** |
| **`concat` 融合建了不用的逐分支 heads** | 3 分支时 **24 个参数无梯度** → 虚增参数量、污染优化器 | `concat` 下 `heads` 留空；**建完模块必查 `p.grad is None`** |
| **判据关键词集合不全（错 3 次）** | 只查 `pillar` → 把 `voxel25`(+0.0279) 误标成"同族容量调整"；再漏 `ms`/`pv` 前缀 → 把冠军误报成 `voxel25_z64` | 关键词集合必须覆盖**全部命名族**；新增命名族时同步更新 |
| **"按名字筛选"的 CLI 未校验名字存在** | `--only voxel25` 但列表里没有 → **不报错、静默跳过**，导致"以为跑过其实没跑" | 启动时校验名字并列出合法名 |
| **`-File script.ps1 -Arr @(a,b)` 把数组绑成位置参数** | 报"找不到接受实际参数 a" | 待办清单**写进脚本内部** |
| `torch.unique(return_inverse=True)` 返回**二维** index | `index_reduce_`/`index_add_` 要求一维 | `.reshape(-1)` |
| `index_add_`（就地）与 `index_add`（返回）混用 | 就地版易漏赋值 | 统一 `x = x.index_add(...)` |
| 填栅格图按"柱出现顺序"而非栅格坐标 | **不报错**，但等价于对空间做随机置换，3×3 卷积失去意义 | 按 `(gx,gy,gz)` 落像素 |
| 一次性 `Conv2d` 放进 `for` 循环重复调用 | 第二层通道不匹配 | 逐层串联成 `nn.Sequential` |

**方法论三条**：
1. 判"某分支坏没坏"用**能否过拟合单房间**（同房 >0.8 = 有容量），不能用跨房 mIoU。
2. 遇到"分数低"先看**训练时间是否异常**（区分"任务难"与"梯度没了"），再看 **loss 首值**，最后才看 mIoU。
3. **在确认实现正确之前，绝不对"某表示/方法是否有效"下结论** —— 本项目为此误判两轮
   （把装配 bug 当成"柱状表示不适合室内"）。

**另一条**：`exit -1073740791`（`0xC0000409`，无 Python traceback）是**间歇性原生崩溃**，
同命令重跑即正常。表每 cell 落盘 → 用自包含重试脚本跑到完成，**不要追这个 bug**（重试成本 ≤1 cell）。

## 9. 真正的进化闭环（本项目最重要的方法论产出）

### 9.1 前两轮为什么不是"真正的进化"

| 轮次 | 搜索空间 | 新架构能否被**真实**评估 | 实测结果 |
|---|---|---|---|
| `pareto` | 63 个**预先测好**的固定点 | ❌ 只能挑名字 | best 出现在 iteration 1，60 迭代只有 4 个不同分数 |
| `pareto-gen` | 组合空间（能提新架构） | ⚠ 只有**估计精度** | `is_synthetic` 0→11，但估计值赢不过实测强项 |

**根本原因**：要达到真正的进化，三个条件缺一不可 ——
- **A. 空间够大**（不能只是我手工枚举的 88 个配置）
- **B. 新架构能被真实评估**（不能只有估计值）
- **C. 奖励无结构性天花板**（估计精度会系统性压制探索）

### 9.2 三个条件如何逐条补齐

**条件 A → `nas_ptseg/arch_space.py`**
用"**砖块**"组合描述架构：分支族（voxel / pillar / rangeview / points）
× 每分支独立参数（体素边长、z 分层、特征宽度、层数）
× 分支数 1~5 × 融合方式 3 种。
**组合数 ≈ 3.2×10^8**（对比手工枚举 88 个）。

架构串语法：`<branch>[,<branch>...]@<fuse>[|feat=N]`

```
voxel20_z32,voxel50_z96@gate                          2 分支，混合体素尺寸
voxel15_z64,voxel15_z192,voxel35_z96@concat|feat=128  3 分支 + feat 轴
```

**条件 B → 架构串可直接实测**
`multibranch_exp` 的 `_known()` / `_arch_spec()` 识别架构串 →
**无需注册到 CONFIGS 就能训练**。
否则每次新组合都要手工加配置，**等于把人变成搜索的瓶颈**。

**条件 C → 精度绝不估计**
> **成本可估，精度必须实测。**

| | 由什么决定 | 能否从结构推出 | 本项目的做法 |
|---|---|---|---|
| **成本** | 结构（分支数 × z 分层 × 体素尺寸） | ✅ 可以稳定外推 | 用实测锚点拟合的模型估算（比值 0.75~1.23） |
| **精度** | **优化过程** | ❌ **不能** | **一律留空**，必须实测才有值 |

强行估精度会**系统性压制探索**（实测印证：第一版保守估计把探索压到 0）。
现改为：新架构只给成本，精度标 `pending` → **不参与打分**，
作为"待实测建议"交给闭环执行器训练。下一轮搜索就能读到**真实精度**
→ **新架构没有任何"估计值天花板"**，它可以凭实测结果胜过任何已知配置。

**闭环执行器 → `nas_ptseg/arch_loop.py`**
`propose_by_sampling()` 是**不依赖 LLM** 的自主提出器，
以"精度最高的**可信**实测"为锚点做**单轴邻域扰动**，优先低成本。
两个必须保留的防守：
1. 锚点必须过滤"不可信实测"（`_reliable_archs(min_cells=20)`）——
   否则一次 1 房 2 epoch 的冒烟测试（假高分）会把整个采样邻域带偏。
2. `_hand_config_archs()` 把 66 个手工配置转成架构串并排除，避免重复实测。

### 9.3 ✅ 结果：闭环搜出了我从未想到的冠军

**第一轮提出 4 个架构**（对当时冠军 `ms3_mix_v20_v50_z16_z32_z96` 做单轴扰动）：

### 9.4 ⚠⚠ 方法论修正：**"选择"用枚举，"提出"才用 LLM**

在把 7 个进化架构写回候选池后（63 → 70 个），重跑 LLM 搜索时**又一次静默崩溃**，
这促使我重新审视整个设计：

> **候选池是有限的（~70 个已实测），目标函数是确定的。
> 在有限集上求确定目标的最优 → 枚举就是精确解**
> （确定性、瞬时、保证最优）。
> 让 LLM 反复生成策略来"选"一个有界集合里的元素，是绕远路。

**实测证据**：直接枚举 70 个候选：

```
最优 = voxel15_z16,voxel20_z32,voxel50_z96@gate
  mIoU 0.4126（基线 0.3370，Δ = +0.0756）
  combined 0.4244     ← 比两轮 LLM 搜索的 best（0.4216）高 0.0028
  成本 26.7 ms（快 3.9×）
  来源 = 进化产出
```

**即：LLM 搜索卡在 0.4216，而真正的最优 0.4244 就躺在候选池里没人选。**
根因：`initial_program_pareto.pareto_policy` 一直返回一个早期坏基线
（`"voxel25_z64"`），搜索从错误位置起步。

**正确的分工**（已落地）：

| 环节 | 工具 | 理由 |
|---|---|---|
| **提出**新架构 | `nas_ptseg/arch_loop.py`（采样）/ LLM | 需要创造力；空间 **3.2×10^8**，枚举不了 |
| **选择**最优 | **`nas_ptseg/pareto_select.py`（枚举）** | 候选**有限**、目标**确定** → 枚举即最优 |
| **验证** | 真实训练后写回表 | 摆脱"估计值天花板" |

**LLM 的价值在"提出"，不在"选择"。** 把这两件事分开，系统才既可靠又最优。

### 9.5 闭环运行中的工程防守（都会静默失败）

| 坑 | 症状 | 正解 |
|---|---|---|
| **`|` 是 Windows 文件名非法字符** | 架构串 `\|feat=N` 进文件名 → `open()` 抛 `PermissionError` → **崩在第一格、表完全不存在**；外层 `_table_complete` 永远 False → **无限重跑**；而 subprocess `returncode` 仍可能为 0 → **报"成功"**（三层掩盖，极难定位）。**后果：整条 `feat` 轴静默不可测** | ① `arch_space.safe_filename()` 只替换文件名（表内 `name` 仍存原串，**切勿从文件名反推**）；② 写/读两处**共用同一函数**产文件名；③ **不要只信 returncode**，每轮用 `_table_complete` 复核产物 |
| **成本模型漏掉某个轴** | `estimate_cost` 不建模 `feat`：5 分支 `feat=128` 实测 **131.6 ms**（比基线还慢），模型给 **46.7 ms**（低估 2.8×）→ 一个实际最慢的配置会被当成"便宜的" Pareto 点 | 成本模型必须覆盖**所有**影响耗时的轴；每加一个轴就用实测锚点校准（现 `feat` 缩放 `(feat/64)**1.5`，ratio 1.00） |
| 正则用嵌套量词匹配长文件 | **原生栈溢出** `0xC0000409`，**exit 1 且无任何回溯** → 极易误判成"环境坏了" | **逐行匹配 + 显式字符类**，把回溯压到常数级 |
| 扫描范围过窄 | 漏掉自建目录里的表 → "明明测过了却显示未测" → **重复烧 GPU** | 扫 `data/*/` 全部目录 |
| 只判断"文件是否存在" | 崩溃时文件已存在但内容不全（曾出现 276/288） | **显式数 cell 数** |
| 实测不走重试路径 | 一次原生崩溃白等一整轮（曾 19 分钟零进展） | 所有实测走 `arch_loop.measure(max_rounds=10)` |
| **不完整的表被当结论用** | `...voxel35_z48@gate` 在 n=18/24 时均值 0.4185（看着破纪录），**跑完 0.4121** | 判断任何"新纪录"前**先检查 cell 数 ≥24** |
