**根本问题**：三个条件缺一不可 ——

**B. 新架构能被真实评估**（不能只有估计值）
**C. 奖励无结构性天花板**（估计精度会系统性压制探索）

#### 6.2 三个条件逐条补齐

**条件 A → `nas_ptseg/arch_space.py`（新）**
用"**砖块**"组合描述架构：分支族（voxel/pillar/rangeview/points）×
每分支独立参数（体素边长、z 分层、特征宽度、层数）× 分支数 1~5 × 融合方式 3 种。
**组合数 ≈ 3.2×10^8**（vs 手工枚举 88 个）→ 这是"能搜出预料不到组合"的前提。

架构串语法：`<branch>[,<branch>...]@<fuse>[|feat=N]`
例：`voxel20_z32,voxel50_z96@gate`、`voxel15_z64,voxel15_z192,voxel35_z96@concat|feat=128`

**条件 B → 架构串可直接实测**（已打通）
`multibranch_exp.py` 的 `_known()` / `_arch_spec()` 现在能识别架构串 →
**无需注册到 CONFIGS 就能训练**。端到端冒烟已验证：
`voxel30_z48@gate`（三个轴都是新组合）直接落表为 `voxel30_z48@gate_k48_ep2.json`。
⚠ 这一步很关键：否则每次新组合都要我手工加 CONFIGS，**等于把人变成搜索的瓶颈**。

**条件 C → 精度绝不估计**（`evaluator_pareto._synth_from_spec` 第三版）
> **成本可估，精度必须实测。**

理由：成本由**结构**决定（分支数 × z 分层 × 体素尺寸），可稳定外推；
精度由**优化**决定，**无法从结构推出**。强行估精度只会系统性压制探索
（第一版保守估计把探索压到 0，第二版加固定奖励也只是"奖励猜测"而非"奖励发现"）。
现改为：新架构只给成本，精度标 `pending` → **不参与打分**；
评估器把它作为"待实测建议"返回，由 `arch_loop.py` 真训练并写回表。
下一轮搜索就能读到**真实精度** → **新架构没有任何"估计值天花板"**。

#### 6.4 本轮踩到的两个坑（都会静默失败）

**坑 1：正则回溯把进程打崩，且不留任何回溯信息。**
`extract_from_evolve` 初版用 `(?:,?[a-z0-9_]+)*` 这种嵌套量词匹配**整个长文件**，

**exit code 1 且 stdout/回溯全无** → 极容易误判成"环境坏了"。
修法：**逐行匹配 + 显式字符类**（架构串字符集很小：字母/数字/下划线/逗号/@/|/=），
把回溯压到常数级；并对单文件 >2MB 直接跳过。

**坑 2：`measured_archs()` 扫描范围过窄 → 会重复训练。**

表现为"明明测过了却显示未测" → **重复烧 GPU**。
修法：扫 `data/*/` 全部目录。

**坑 3：PowerShell 里 `@` 是数组运算符。**
`Get-ChildItem "*@*"` 这类命令会静默失败/无输出。查含 `@` 的文件要用
Glob 工具或 Python 的 glob，不要在 PowerShell 里直接写 `@`。

#### 6.11 ⚠⚠ 重要的方法论修正：**选择用枚举，提出才用 LLM**

**触发**：用扩展后的候选池（70 个）重跑 OpenEvolve 搜索，
进程**又一次静默崩溃**（iteration 0 后 26 分钟无进展，进程已消失，无回溯）。

**借这次机会做的关键反思**：
> **候选池是有限的（~70 个已实测），目标函数是确定的。
> 在有限集上求确定目标的最优 → 枚举就是精确解，确定性、瞬时、保证最优。
> 让 LLM 反复生成策略来"选"一个有界集合里的元素，是绕远路。**

**实测证据**：写完 70 个候选后**直接枚举**，得到
```
最优 = voxel15_z16,voxel20_z32,voxel50_z96@gate
  mIoU 0.4126（基线 0.3370，Δ = +0.0756）
  combined 0.4244     ← 比两轮 LLM 搜索的 best（0.4216）高 0.0028
  成本 26.7 ms（快 3.9×）
  来源 = **进化产出**
```
**即：LLM 搜索卡在 0.4216，而真正的最优 0.4244 就躺在候选池里没人选。**

**根因**：`initial_program_pareto.py` 的 `pareto_policy` 一直返回
`"voxel25_z64"`（一个早期坏基线），搜索从错误位置起步，LLM 得从头重新发现。

**修正 —— 正确的分工（已落地）**：

| 环节 | 工具 | 理由 |
|---|---|---|
| **提出**新架构 | `nas_ptseg/arch_loop.py`（采样）/ LLM | 需要创造力；空间 3.2×10^8，**枚举不了** |
| **选择**最优 | **`nas_ptseg/pareto_select.py`（枚举）** | 候选有限、目标确定 → **枚举即最优** |
| **验证** | 真实训练后写回表 | 摆脱"估计值天花板" |

**LLM 的价值在"提出"，不在"选择"。** 把这两件事分开，系统才既可靠又最优。

**本轮交付**：
1. **`nas_ptseg/pareto_select.py`（新）**：双目标选择的精确解。
   `combined = mIoU − λ·log10(cost/base_cost)`（λ 默认 0.02；
   成本**必须取对数**，跨 25×，线性惩罚会否决整个 Pareto 左侧）。
   给出完整适应度排序 + **真实 Pareto 前沿**（按成本升序、只留精度创新高的）。
   为此把 `evaluator_pareto.py` 的候选加载逻辑**复用**（不另写一份，避免两处漂移）。
2. **`evolve/initial_program_pareto.py`**：`pareto_policy` 改为返回
   **枚举出来的精确最优** `voxel15_z16,voxel20_z32,voxel50_z96@gate`，
   让搜索从正确位置起步。

**适应度前 8 名（70 个候选）**：

#### 6.12 ⚠⚠ 修掉一个**测试集泄漏**（必须记住）

2. **`evaluator_pareto.py` 加 `_synth_from_spec()`**：

   因为它取"同分支数的最差实测值"，**结构上不可能超过同分支数的最佳实测值**

   - 但**在 60 迭代的预算内，进化没能提出一个胜过实测冠军的新组合**
   - 这符合预期：新架构的估计值取"同分支数最差值 + 有限奖励"，
     要胜过已被实测证明很强的配置，需要进化真的找到更好的组合，而非估计偏置

   把进化提出的**高分新组合**真实训练一遍（它们分数 0.413~0.418，接近冠军，
   但都属于"估计"），用实测确认或否证 —— 这才是把生成式搜索闭环的唯一方式。

#### 5.3 ⚠⚠ 一个必须记住的失败模式：**LLM 会编造机制来自我合理化**
最终 `best_program.py` 把 `pareto_policy` **改回了返回字符串**，并写下理由：

> "历史反复验证：返回 list 时评估器在方差噪声下会偶尔选中低分项，
> 直接压低权重最高的 `min_domain`（**占适应度 0.5**）；单字符串锁定峰值最稳。"

**这段推理是错的**：`min_domain` 及其 0.5 权重是**旧版 `evaluator.py`（k 空间）的设计**，
当前的 `evaluator_pareto.py` **根本没有 `min_domain` 这个指标**。
→ **LLM 编造了一个不存在的机制，用它解释了"为什么退回字符串更好"**，
而这个"更好"恰好是它自己放弃探索新架构的结果。

**为什么危险**：这段注释读起来**非常像真实的实验结论**（有具体数值、有"反复验证"、
有机制解释），如果不逐条核对评估器源码，很容易被当成有效知识带进后续迭代
（甚至写进论文）。而且它**自我强化**：一旦被当成理由写进代码，后续变异会继续沿用。

**防线**（必须保持）：
1. `is_synthetic` 这类**客观可观测字段**是唯一可信的探索证据 —— 不要相信注释里的自我陈述。
2. 看到程序注释里引用**具体机制/权重/指标名**时，**必须回源码核对该机制是否存在**。
3. 评估器的 artifact 报告要**明确指出"当前评估器有哪些指标"**，
   减少 LLM 借用旧机制的空间（已在 `_build_report` 里列出全表）。

**修掉的 3 个启动问题**（均在 `evolve/run.ps1`）：
1. `$Space` 的 `ValidateSet` 只有 `{k, arch}` → 加 `pareto` / `pareto-gen`
2. pareto 分支缺预检 → 加"统计有多少张表带实测 `step_sec`"的检查（<4 张则报错）
3. **PowerShell 把 evaluator 的 stderr 当终止错误**：evaluator 有意把候选摘要打到 stderr
   （不污染 stdout 的 metrics JSON），而 `$ErrorActionPreference="Stop"` 会因此**中止启动器**，
   尽管 evaluator 其实成功了。已在调用处临时放宽为 `Continue`（真正的门禁仍是 exit code）。
   ⚠ 另注：`Write-Host` 字符串里**不要用反引号转义引号**（`` \` ``）—— GBK 解码下会解析失败。

**关键经验（对后续所有"LLM 提出新候选"的搜索都成立）**：
> **保守估计必须配探索奖励，否则搜索会退化成"复述已知候选"。**
> 奖励要给得刚好能进候选、又不能压过实测 —— 这个平衡是这类搜索的核心设计点。
