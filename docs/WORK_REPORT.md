## 二、做成了什么

### 2.1 建立了一条可靠的"真实评估"闭环

这是本项目最实在的工程产出，分三步：

| 环节 | 工具 | 作用 |
|---|---|---|
| **提出** | `nas_ptseg/arch_space.py` | 架构串语法 `<branch>[,<branch>...]@<fuse>[|feat=N]`，组合数 ≈3.2×10^8 |
| **实测** | `nas_ptseg/arch_loop.py` | 架构串**免注册直接训练**；10 轮重试；自动排除已测 |
| **选择** | `nas_ptseg/pareto_select.py` | 双目标精确解（枚举），输出真实 Pareto 前沿 |

关键设计决定（有实测支撑）：
- **成本可估，精度绝不估**。精度由优化过程决定，无法从结构外推；
  强行估计会系统性压制探索（实测：第一版估计把探索压到 0 次）。
- **选择用枚举，提出才用 LLM**。候选池有限（~100）、目标确定 → 枚举即精确解。
  实测：两轮 LLM 搜索 best = 0.4216，**不如直接枚举的 0.4244**。

### 2.2 找到了手工设计不出的冠军

冠军是 5 个不同体素尺寸的混合（0.15/0.20/0.25/0.35/0.50 m），
每层配各自独立的 z 分层（16/24/16/64/96）。
此前手工枚举 88 个配置的最好结果是 0.4110。

### 2.3 提清了四条可复用的规律（均有实测支撑）

1. **z_bins 倒 U，单尺度峰值 ≈64**
   （voxel25：z8 0.3290 → z64 0.3885 → z192 0.3806）
2. **voxel_size 倒 U，峰值 ≈0.20 m**
   （v50 0.3685 → v20 0.3902 → v15 0.3879）
3. **收益来自"加分支"，不来自"调参数"**：加第 4/5 分支 +0.0021/+0.0033；
   而粗端参数调整全部 −0.0001 ~ −0.0028
4. **各层贡献可排序**（留一消融）：
   `v15(−0.0076) > v20(−0.0049) > v50(−0.0046) > v35(−0.0034) > v25(−0.0033)`

### 2.4 完成了三条轴的系统性排查

| 轴 | 判定 | 关键证据 |
|---|---|---|
| 尺度/分支 | 有效，但**已收敛** | 边际增益 +0.0033 → +0.0001（< σ） |
| 尺度参数微调 | **局部有效、不可推广** | v25 降 z 是严格 Pareto 改进；v20/v35 降 z 全部变差 |
| 特征宽度 feat | **负结果** | feat=128 花 2.2~3.0× 成本，精度**下降** 0.004~0.006 |

### 2.5 完成的验证工作

- **test split 无偏验收**：test 排序与 val 排序**完全一致**（0.4210 > 0.4194 > 0.4184）
  → 基于 val 的搜索确实迁移到 test
- **留一消融**：每层都有正贡献，v25 贡献最小
- **反向对照**：v25 的 z16→z32 得 0.4160（−0.0033），确认第 5 轮改进非噪声

## 三、没做成什么 / 被否证的

### 3.1 原课题核心假设被否证

**「架构随密度/房间/域条件化能解决跨域」——不成立。**

- 架构表（6 配置，参数量全部 113,415）：逐房间 headroom **+0.0000**；
  域级（逐 Area）也 **+0.0000**；6 个 Area 的最优**全部**是同一个配置
- 探针：极差 0.0419 / 3σ = 2.76 → **有主效应**，但**零交互**
- 结论：收益来自"选一个更好的普通架构"，不是"让架构随条件变化"

### 3.2 k 轴已榨干

`headroom.py` @full@300：最好固定 k=48 = 0.3365；逐房间 oracle 0.3382
（headroom **+0.0017** < σ_fit 0.0014）。
三个独立角度关闭：密度 R²=0.008、尺度 R²=0.018、类别数 R²=0.001。

### 3.3 两条没能收敛到理想状态的路

- **短预算代理**：ρ(cheap@25ep, full) = **−0.825**（负相关）；
  翻转点在 25~50 ep 之间。50 ep 起 Δ 恒为 +0.032。
  fitness 口径救不了短预算（固定预算下 regret 只是 mean 的仿射变换，ρ=+1.000）。
- **range-view 表示**：单独最弱（rv64 0.2786，低基线 0.058）；
  分辨率扫描几乎平坦（rv32/64/128 无差）；
  且**弱分支参与融合会拖累**：`pts+rv64` = 0.3279 **低于基线**。

### 3.4 已撤回的旧结论

- **"柱状/BEV 在室内不可用"** —— 已撤回。旧的 0.04 是装配 bug 的产物。
  修后 `pillar25` = 0.3313（仅低基线 0.015），单 run 2.3s vs points 32s（**快 14 倍**）。

## 四、工程问题记录（每条都曾差点产出错误结论）

| 问题 | 症状 | 处理 |
|---|---|---|
| **`|` 是 Windows 文件名非法字符** | `|feat=N` 进文件名 → `PermissionError` → 崩在第一格、**表完全不存在**；外层无限重跑；`returncode` 仍为 0 → **报"成功"**。**整条 feat 轴静默不可测** | `safe_filename()` 统一处理；写/读共用同一函数；不再只信 returncode |
| **成本模型漏掉 feat** | 实测 131.6 ms，模型给 46.7 ms（**低估 2.8×**）→ 最慢配置被当成"便宜的" Pareto 点 | 加 `(feat/64)**1.5` 缩放，校准后 ratio 1.00 |
| 正则嵌套量词匹配长文件 | **原生栈溢出** `0xC0000409`，exit 1 且无回溯 | 逐行匹配 + 显式字符类 |
| 扫描范围过窄 | 漏扫目录 → 重复烧 GPU | 扫 `data/*/` 全部目录 |
| 只判断"文件是否存在" | 崩溃时文件已存在但内容不全（276/288） | 显式数 cell 数 |
| 实测不走重试路径 | 一次崩溃白等一整轮（曾 19 分钟零进展） | 统一走 `arch_loop.measure(max_rounds=10)` |
| 不完整的表被当结论 | n=18/24 时 0.4185（看着破纪录），**跑完 0.4121** | 判"新纪录"前先确认 cell 数 ≥24 |
| **测试集泄漏** | `_tval` 验收表被扫进搜索 → 冠军值显示 0.4184（test）而非 0.4126（val） | 显式排除 `_tval`；验收表与搜索表机制隔离 |
| 性能测量未 warmup | `z_bins=8`（真实 1.0ms）被量成 238 ms → **Pareto 前沿整体反向** | warmup 3 次 + synchronize |

**反复出现的问题**：间歇性原生崩溃（`0xC0000409`）已发生 **7+ 次**，无 Python 回溯。
已通过"表每 cell 落盘 + 多轮重试"绕过，未根治。
