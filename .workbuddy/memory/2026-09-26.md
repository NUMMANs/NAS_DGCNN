### ⚠⚠ 发现并修掉成本模型的一个 2.8× 低估

第一次探测就直接给出一个决定性事实：
**5 分支冠军 + `feat=128` 实测 131.6 ms/step**（峰值 1176 MiB）——
**比 `points` 基线（104 ms）还慢**，所以该配置不可能是 Pareto 最优。

而 `arch_space.estimate_cost()` 当时**根本不建模 `feat`**，预估只有 **46.7 ms**（低估 2.8×）。
**后果严重**：合成候选的成本被算小 → combined 被算大 →
**一个实际比基线还慢的配置会被当成"便宜的" Pareto 点**，污染 MAP-Elites 成本轴。

**已修**：`estimate_cost(branches, fuse, feat=64)` 增加 `(feat/64)**1.5` 缩放。
校准结果（对实测锚点）：
```
feat=64   est=46.7   actual=39.5   ratio=1.18
feat=128  est=132.2  actual=131.6  ratio=1.00   ← 修前 0.35
feat=64   est=27.8   actual=26.7   ratio=1.04
```

### ⚠⚠⚠ 修掉一个**让整条 feat 轴静默不可测**的 bug（本次最有价值的发现）

**症状（三层掩盖，极难定位）**：
1. `arch_loop` 报 **`exit=0`**（看起来成功）
2. 但 `data/multibranch_evolved7/` **一张表都没有**
3. 日志里 `[cost]` 行**重复出现 10 次**（说明外层在反复重跑同一配置）

**根因**：**`|` 是 Windows 文件名的非法字符**。
架构串里的 `|feat=N` 直接进入结果表文件名 →
`open(path,"w")` 抛 **`PermissionError(13, 'Permission denied')`**（实测确认）。

**失败链条**：
```
feat=32 架构 → 文件名含 "|" → 第一格写盘 PermissionError
  → 进程崩在第一格、表完全不存在
  → arch_loop 的 _table_complete 永远返回 False
  → 外层无限重跑同一配置（日志里 10 次 [cost]）
  → 而 subprocess 的 returncode 在某些路径上仍是 0 → 宣告"成功"
```

**后果**：**`feat != 64` 的架构全部写不出去 → 整条特征宽度轴静默不可测**。
如果不是我坚持"trace 到根因再往下推"，这个 bug 会让我得出
"feat 轴没有收益"的**完全错误的结论**。

**修法（3 处，必须同步）**：
1. `arch_space.safe_filename(name)`：把 `* ? " < > | : \ /` 替换为 `_`。
   ⚠ **只用于文件名**；结果表内的 `name` 字段仍存**原架构串**，
   所以读回来能精确匹配（`_load_candidates` 就是这么做的）。
   **切勿从文件名反推架构串** —— 必须读表内的 `name`/`config`。
2. `multibranch_exp.run_config` 与 `arch_loop._table_path` **共用同一个函数**产文件名
   （两处各写一份必然漂移 → 找不到表 → 死循环。本次就是两处不一致 + 非法字符叠加）。
3. **`arch_loop` 不再只看 returncode**：每轮都用 `_table_complete` 复核，
   若 `exit=0` 但仍未完成，**主动置 rc=1 并继续重试**，同时打印期望路径。
   > **教训：子进程 returncode 不是"是否真的写完了"的可靠判据，**
   > **唯一可信的是产物本身存不存在、完不完整。**

**验证（端到端）**：
```
safe_filename("voxel20_z32@gate|feat=32")  ->  "voxel20_z32@gate_feat=32"
写盘 OK；_table_complete = True
measured_archs 读到该架构（name 仍是原串 "@gate|feat=32"）
evaluator._find_tables 收到表；_load_candidates 产出候选
```

### 结论速览

| 骨干 | 判定 | 关键实测证据 |
|---|---|---|
| **PTv3** | ❌ **太慢，NAS 不可行** | 实测（4090 单卡，S3DIS 16k 点，46.2M 参数，纯 PyTorch 路径）：grid 0.02 → **16908 ms/step（22.7G 显存）**；grid 0.05 → **6344 ms**；grid 0.10 → 298 ms。**grid 0.05 是 DGCNN 的 61× 慢** → 一张表（24 cells）要 12.7 小时 |
| **PolarNet** | ❌ 表示先天失配 | 极坐标 BEV 与室内几何不匹配（range-view 已预演：rv64 仅 0.2786，且分辨率扫描平坦）→ 在失配表示上做 NAS 没有说服力 |
| **PointViG** | ✅ **选它** | 轻量（5.3M 参数）+ **原生 S3DIS 评测（71.7% mIoU）** + **有尺度轴**（Ball-Query 半径 r=0.2 是它论文里唯一的感受野旋钮）|

### ⚠ 两个必须记住的实测事实

**① PTv3 是纯 backbone，没有分割头。**
`forward(data_dict)` 只返回 `Point` dict（`feat` 等），**构造参数里没有 `num_classes`**，
`grid_size` 也不在构造参数里（在 data_dict 传）。
接分割头要自己写（我实测用 `nn.Linear(64, NC)`，因 dec 输出通道 = `dec_channels[0]` = 64）。

**② PTv3 成本对 `grid_size` 极敏感，且粗网格反而更好训。**
```
grid=0.02  step=16908 ms  peak=22673 MiB  loss=2.355
grid=0.05  step= 6344 ms  peak=20756 MiB  loss=0.911
grid=0.10  step=  298 ms  peak=14339 MiB  loss=0.623
```
→ **grid_size 本身就是一条强搜索轴**（PTv3 用**单一** grid_size 作为全部阶段下采样基础，
又是一个"人类设定单尺度"的设计选择）。
⚠ **本机未装 `flash_attn`**，以上用 `enable_flash=False` 纯 PyTorch 路径测的，
比官方配方慢；装它需编译 CUDA 扩展，torch 2.1 + 4090 有兼容风险。

### PointViG 论文给出的复现规格（已从论文正文挖出）

| 组件 | 规格 |
|---|---|
| **Ball-Query** | **r = 0.2**、**m = 64**（球内补点）、**k = 32**（子图采样邻居数）|
| **关键细节** | 对 Ball-Query **加了 masking**，屏蔽 padding 的无效填充点（否则无效点会被选进子图）|
| **编码器** | 5 stage，下采样比 `(1,4,4,4,4)`，每 stage block 数 `(1,2,3,2,2)` |
| **阶段分工** | Stage 1：grouping-MLP-pooling；**Stage 2~5：自适应空洞图卷积 ADGC** |
| **目标数字** | S3DIS **71.7% mIoU**，5.3M 参数 |

### ⚠⚠ 性能优化：让 NAS 从"不可行"变"可行"

**初版 1.08 s/step —— 比 DGCNN（104 ms）还慢 10×，NAS 完全不可行。**

逐组件计时定位瓶颈：
```
FPS 16384->4096      0.549 s   ← 占整步 63%，唯一主瓶颈
FPS 4096->1024       0.132 s
knn(k=32) 16384      0.055 s
ball_query(r=.2,m=64) 0.060 s
cdist 16384x4096     0.002 s
```

**关键认知：FPS 天然串行，向量化救不了它。**
朴素 0.549 s → 向量化（`cdist` 一次算好）后 **0.499 s**，几乎没变 ——
成本在 `npoint` 次迭代本身（每轮都要在 N 个点上取 argmax）。

**解法：双策略降采样**
- `npoint > 512`（第 1 级）→ **体素网格降采样**：一次性、无循环、O(N)
- `npoint ≤ 512`（后续级）→ 真 FPS（迭代次数少，代价可接受）

**效果**：
```
降采样 16384->4096:  0.549 s → 0.0005 s   （~1000×）
训练步 [single]:     1.08  s → 0.123 s    （8.8×）
```
**现在 118~186 ms/step，与 DGCNN（104 ms）同量级 → NAS 可行。**

> **判断依据**：对 NAS 而言**下采样算子的具体形式不是搜索变量**，
> 所以用网格近似合理；真正要搜的是 ADGC 的**半径集合**。

### 踩到并修掉的 5 个 bug（每个都值得记）

| bug | 症状 | 根因 |
|---|---|---|
| **`v[:, nbr]` 按 dim0 索引** | 通道/样本错位但**不报错**（静默！） | 邻居索引 `(N,kk)`、`v` 是 `(C,N)`，直接索引取错维度。正解 `v.T[nbr].permute(2,0,1)` |
| **缺解码器** | `batch_size (64) vs target (16384)` | 只编码不下采样回填 → 输出 64 点却要 16384 标签。论文同样有 5 stage 编解码 |
| **插值用错坐标** | 最近邻算在全错坐标上（**不报错**） | 粗层点集**不是** `xyz0` 前 N 个点（降采样乱序抽取）→ 必须记 `xyz_hist[s]` |
| **`dec_blocks[s-1]` 下标反序** | 宽度全错（768 vs 96） | blocks 按 `s=4,3,2,1` 顺序 append → `s=4` 对应 `[0]`。用**顺序计数器** `di` |
| **head 宽度写 `c`** | `mat1 [16384,32] × mat2 [512,128]` | head 输入是**解码末轮输出宽** `widths[0]`，不是编码器 `widths[-1]` |

**加的三条断言**：解码每级宽度匹配、解码后点数回到 N0、head 宽度匹配。
> **教训：`nn.Linear` 的形状报错（如 96x32）完全看不出是哪一级出的问题。
> 在循环体内加显式断言，比事后从 `nn.Linear` 报错倒推快得多。**

- 后果：每次调 `cl` 都会去编译一个不存在的源文件 `EHsc` → **退出码 2**
  → 表现为 torch 报 `Error checking compiler version for cl: Command 'cl' returned non-zero exit status 2`，
    **且 nvcc 静默失败（exit 2，不打印任何错误）** —— 极难定位
- **修复**：任何 Windows 原生编译前必须 `set CL=` / `set LINK=` **清空**
- ⚠ 这个 `CL` 还会带 `/D_DEBUG` → 若首次编译残留了 debug obj，**链接时报 `LNK2038`
  `_ITERATOR_DEBUG_LEVEL` 0 vs 2、`RuntimeLibrary` MD vs MDd** → 必须**先删 build 目录**再重建

**坑 2：Windows SDK 没有接进构建环境（不是"缺失"）**
- SDK 实为 `D:\Windows Kits\10\`（注册表 `KitsRoot10`），含 10.0.22621.0 等三版，`ucrt\stddef.h` 齐全
- 直接调 `setup.py` 时 torch 的 `_get_vc_env()` 没把 D 盘 SDK 注入 `INCLUDE` → `C1083: stddef.h`
- **修复**：在 `cmd` 里先 `call vcvars64.bat`（它按注册表补齐），再设 `DISTUTILS_USE_SDK=1`

**坑 3：MSVC 14.43 的 STL 要求 CUDA ≥ 12.4，而本机只有 CUDA 12.1**
```
yvals_core.h(921): error: static assertion failed with
  "error STL1002: Unexpected compiler version, expected CUDA 12.4 or newer."
```
- `yvals_core.h` 第 918 行：`#ifndef _ALLOW_COMPILER_AND_STL_VERSION_MISMATCH`
  → **官方旁路宏就是 `_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH`**
- **修复**：`set NVCC_PREPEND_FLAGS=-D_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH`
  （用 `NVCC_PREPEND_FLAGS` 注入 → **不必修改上游 setup.py**）
- ⚠ 我一开始只读了 nvcc 自己的 `crt\host_config.h`（判据 `_MSC_VER ∈ [1910,2030)`，
  14.43→1943 通过就以为没问题），**漏了 STL 这一层的更严限制**。教训：编译器版本检查可能有多层。

### ✅ 可复用的构建配方（`_sdk/build_pn2.bat`）

### ⭐ 搜索轴确认（这是本轮最重要的技术结论）

`PointNextEncoder._to_full_list`（`openpoints/models/backbone/pointnext.py` L391）：
- **`radius` 传标量** → 按固定公比自动铺开：`[[0.1],[0.1],[0.2],[0.4],[0.8]]`
- **`radius` 传 list** → **按"每个 stage 一个值"解释**（blocks 全是 1）
  ```python
  if isinstance(param, List):
      for i, value in enumerate(param):
          param_list.append([value])      # 每 stage 独立
  ```
→ **搜索变量就是一个干净的 5 元组 `(r0, r1, r2, r3, r4)`**，
   且**上游原生支持**（不是我们 hack 出来的）→ 可复现性极强。

**命题**（比 PointViG 那条更好，因为不用自建、不会被"实现错"推翻）：
> PointNeXt 的 S3DIS 基线把 5 层感受野压成**固定公比 ×2 的等比数列**，
> 而代码本就支持**逐层独立半径** —— 这个自由度**从未被使用、从未被消融**。
> NAS 回答：**逐层独立半径是否优于固定公比？**
